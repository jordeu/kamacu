# Quick Task 260728-sm5: Split text/CR write in send_session_message

## Objective

The previous fix (260728-s5a) made the endpoint send `\r` instead of `\n` as the terminator — necessary but not sufficient. Live testing against a real Claude Code session (idle, ready for input) showed:

- **Lone `\r` write:** submits the staged prompt → agent transitions idle → working. ✓
- **Short ASCII message + `\r` in one combined write:** usually submits (paste detection doesn't fire on small ASCII chunks). ✓
- **Multi-byte UTF-8 or longer message + `\r` in one combined write:** paste detection fires in Ink (Claude Code's TUI layer); the CR is consumed as paste content rather than the Enter key; agent stays idle; the prompt text sits in the input box unsubmitted. ✗

The robust fix is to mirror how a human typing reaches the PTY: text in one stdin chunk, the Enter key in the next. That means **two separate `WriteInput` calls** — body, then `\r`.

## Background

Raw-mode TUIs (anything built on Ink / readline / bubbletea) use a paste-detection heuristic on stdin chunks. The exact trigger varies (chunk size, presence of multi-byte UTF-8, speed of arrival), but the consequence is consistent: a chunk that "looks pasted" is buffered for preview, and any embedded CR is treated as paste content rather than the submit key. xterm.js in the browser produces per-keystroke chunks naturally (text arrives in many small `onData` events; Enter is its own event), so human typing never trips paste detection. Our HTTP endpoint was producing one big chunk per request, which looked like a paste.

Splitting the write does not eliminate paste detection entirely — if the message body itself is very long or multi-line, Ink may still flag the body chunk as a paste and show its "paste again to expand" UX. That's the same UX a human gets when pasting, and the MCP tool can't (and shouldn't) work around it. The split-write fix targets the **common case**: a normal-length single-line prompt that should submit on its own.

## Tasks

### Task 1: Split the WriteInput call

**Files:**
- `internal/api/sessions.go` (modify the `input` handler — currently around lines 524-546 after the 260728-s5a fix)

**Action:**

Current shape (post-260728-s5a):

```go
msg := req.Message
msg = strings.TrimSuffix(msg, "\n")
msg = strings.TrimSuffix(msg, "\r")
msg += "\r"
if err := sess.WriteInput([]byte(msg)); err != nil {
    writeError(w, http.StatusConflict, err.Error())
    return
}
writeJSON(w, http.StatusOK, map[string]int{"bytes_written": len(msg)})
```

New shape — two sequential writes, no combined terminator:

```go
msg := req.Message
// Strip any trailing terminator so we control the submit key explicitly.
// The body is written in one WriteInput call; the \\r submit key is written
// in a SEPARATE call. A single combined write of (body + \\r) triggers
// paste-detection in raw-mode TUIs (Claude Code via Ink), which treats the
// embedded CR as paste content rather than the Enter key. Two writes mirrors
// how human typing reaches the PTY (text in one stdin chunk, Enter in the
// next) and is robust regardless of message content/size.
msg = strings.TrimSuffix(msg, "\n")
msg = strings.TrimSuffix(msg, "\r")
if err := sess.WriteInput([]byte(msg)); err != nil {
    writeError(w, http.StatusConflict, err.Error())
    return
}
if err := sess.WriteInput([]byte("\r")); err != nil {
    writeError(w, http.StatusConflict, err.Error())
    return
}
writeJSON(w, http.StatusOK, map[string]int{"bytes_written": len(msg) + 1})
```

Update the comment block above the handler to reflect the split-write rationale (currently it explains CR-vs-LF; expand it to also explain the split-write shape and why).

**Verify:**

```bash
go build ./...
grep -A2 'TrimSuffix.*\\r' internal/api/sessions.go   # confirm no combined msg += "\\r"
grep -c 'sess.WriteInput' internal/api/sessions.go    # input handler should now show TWO calls (plus any other WriteInput refs elsewhere in the file)
```

**Done:**

Handler performs two sequential `sess.WriteInput` calls — body first, `\r` second. No combined terminator. The 200 response reports `len(msg) + 1` bytes written.

## Out of Scope

- Per-character typing simulation (writing each byte of the body as its own WriteInput call). Overkill — paste detection on a single-line body chunk is rare and matches the human-paste UX when it does fire. Two writes (body + `\r`) is the right granularity.
- Backpressure / write-queue management. The two writes happen synchronously; if the first blocks, the second waits naturally. No goroutine needed.
- Changes to the MCP tool (`internal/mcp/sessions.go`) — the tool bridges verbatim to the endpoint; the contract is unchanged.
- Documentation updates to PROJECT.md / ROADMAP.md.
- A future enhancement that lets the caller request "raw mode" (no auto-terminator, no split) for advanced use cases — not needed now; the common case is "send a prompt and have it submit".
