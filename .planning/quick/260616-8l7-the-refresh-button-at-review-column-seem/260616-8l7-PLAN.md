<objective>
Fix the Review-column refresh button so it always re-fetches PR check status.

The refresh button "seems to not be working": some PRs whose checks finished
successfully keep showing the RED dot instead of GREEN even after clicking
refresh.

Purpose: A user clicking refresh expects a real, fresh read from GitHub. Right
now an explicit refresh can be silently swallowed by an anti-spam floor that was
never meant to block user-initiated refreshes — only background polling and
button-mashing.

Output: A one-line guard change in the cache gate plus updated tests proving the
corrected behavior.
</objective>

<root_cause>
Traced end-to-end: check finishes → backend `reduceChecks` → API Result → frontend
query → dot color. The status MAPPING is correct and consistent both ways
(`internal/github/prlist.go:76-121` produces "pass"/"fail"/"pending"/"none";
`web/src/components/board/PRCard.tsx:18-24` maps "pass"→green, "fail"→red). This
is NOT a status-mapping bug.

The bug is a stale-cache / missing-invalidation bug in the backend demand-driven
cache: `internal/github/service.go`, `Service.Get`.

The cache-serving gate (service.go:108-110):

```go
if (!force && e.cached != nil && now.Sub(e.fetchedAt) < cacheTTL) ||
    now.Sub(e.lastAttempt) < attemptFloor ||   // <-- BUG: binds even force=true
    e.inflight {
    // serve stale cache WITHOUT fetching
}
```

- `force=true` (the refresh button, via `?refresh=1`) correctly skips the 60s
  TTL clause (it is guarded by `!force`).
- BUT the second clause, the 10s `attemptFloor`, has NO `!force` guard. Its
  comment (service.go:81, 34) says it "binds every attempt, even force" as
  anti-spam.
- `e.lastAttempt` is set on EVERY `Get` — including the silent 60s background
  poll (service.go:119, `e.lastAttempt = now`).

Reproduction timeline:
1. Background poll fires at T=0 → `lastAttempt=0`, fetches, checks="fail" (red).
2. CI goes green moments later. User sees red, clicks refresh at T=5s.
3. `Get(force=true)` → clause 2: `now.Sub(lastAttempt)=5s < 10s` → serves the
   STALE cached "fail" → no gh call. Dot stays red.
4. The frontend mutation still "succeeds" (the endpoint is always-200 and
   `useRefreshPullRequests.onSuccess` writes the returned stale Result back into
   the cache via `setQueryData`), so there is NO error — exactly matching
   "seems to not be working."

The 10s floor's legitimate job is to stop the 60s background poll and rapid
forced re-clicks from spawning many `gh` calls. But because `lastAttempt` is
bumped by the background poll too, the floor swallows a user's FIRST legitimate
refresh click whenever it lands within 10s of a poll tick — which is common.

Fix: an explicit user refresh (`force=true`) must always fetch. Gate the
`attemptFloor` clause on `!force`. The 60s background poll is already rate-limited
by the TTL (it cannot spawn more than once per 60s), so removing the floor for
forced calls introduces no background-spam regression; the only thing that can
exceed one-call-per-10s is the user deliberately hammering the button, which is
both intentional and rate-limited by the gh round-trip itself.

Evidence files:
- internal/github/service.go:102-137 (Get + the buggy gate)
- internal/github/service.go:80-83 (cacheTTL / attemptFloor consts + intent)
- internal/github/service.go:119 (lastAttempt set on every attempt incl. poll)
- internal/api/pullrequests.go:79-80 (force = refresh=1, passed straight through)
- web/src/api/pullRequests.ts:46-55 (refresh mutation, onSuccess setQueryData)
- web/src/components/board/ReviewColumn.tsx:129-138 (refresh button onClick)
- web/src/components/board/PRCard.tsx:14-25 (checks→color, mapping is correct)
</root_cause>
