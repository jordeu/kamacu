# Quick Task 260728-q5k: start_task_agent MCP tool (MCP-only auto-start reversal)

## Objective

Add one new MCP tool — `start_task_agent` — that lets an agent running inside a Kamacu task PTY spawn (or resume) the agent session for another task. The tool is a thin HTTP bridge: it POSTs `{"kind":"agent","task_id":N,"resume":bool}` to the existing `POST /api/sessions` endpoint and passes Kamacu's response back verbatim via `bridge.call`. This reverses the documented "no auto-start" rule for the **agent-delegate surface only** — the browser's explicit Start button, task-creation flow, and PROJECT.md's "Out of Scope" entry are all untouched. The agent is the user's delegate at the same trust level as `delete_task` and `open_review`.

## Background

Every MCP tool in this codebase is a thin `bridge.call` HTTP client to Kamacu's API at 127.0.0.1:7333 (Phase 06/07 pattern). The orchestrator pre-located the upstream endpoint and the existing per-resource patterns — no research is needed:

- **Upstream target (READ-ONLY — NOT modified):** `internal/api/sessions.go` `(*sessionHandler).create` at line 222 (route `POST /api/sessions`, registered in `internal/api/routes.go`). Body shape `{"kind":"agent","task_id":N,"resume":bool}`. Returns **201** with the session-row JSON on success (`writeJSON(w, http.StatusCreated, sess.Info())` at sessions.go:494). Error codes: **409** "agent session already running" (the one-running-agent-per-task dedup, :310), **409** "task has no worktree" (:269 for task_id<=0, :299 for NULL worktree_path), **409** "no session to resume" (:325/:333), **404** "task not found" (:291). The bridge does NOT reimplement any of these — they all run server-side.
- **Bridge pattern (mechanical repeat):** `bridge.call` (bridge.go:88) does b.do → ReadAll(LimitReader(maxBodyBytes)) → transport-error wrap → non-2xx wrap (`kamacu <m> <p>: HTTP NNN: <body>`) → 2xx TextContent passthrough. The full 2xx range is accepted, so the 201 success passes through cleanly.
- **Closest analogs:** `createTask` (tasks.go:227-231) and `moveTask` (tasks.go:275-279) for the POST-with-JSON-body shape (marshal a `map[string]any`, wrap in `bytes.NewReader`, delegate to `bridge.call`); `openReview` (reviews.go:328-337) for the int-arg + path-rendering shape. This tool combines both: int `task_id` arg + a JSON body.

**Three corrections to the orchestrator brief (bake into the implementation, do NOT follow the brief verbatim):**

1. **InputSchema is `map[string]any`, NOT `mcp.With*` helpers.** The brief mentioned `mcp.WithString/WithNumber/WithBoolean/Required`. That is INACCURATE for this codebase. server.go:79-83 locks the convention: *"The low-level Server.AddTool method is used with an explicit `map[string]any` InputSchema — NOT the typed generic helper."* Every Phase 06-09 tool (sessions.go:98-110, reviews.go:94-103, tasks.go, workspaces.go) uses the map form. AddTool panics if `"type":"object"` + a `"properties"` map are absent (Phase 06 Pitfall 2). **Use the map form** — it is the established, locked pattern.
2. **`withRecover` IS required here.** The brief's "Closest analog is reviews.go" is misleading on this point: `reviews.go` does NOT use `withRecover` (those are synchronous GET/POST bridges). But `sessions.go` — the file we're editing — wraps **every** handler closure in `withRecover` (sessions.go:112, 133, 158, 187). Since we are adding to `sessions.go`, we match that file's own convention: wrap the new closure in `withRecover("start_task_agent", ...)` like its siblings. This is a file-local consistency rule, not a phase-wide one.
3. **`server.go` needs NO edit.** `registerSessionTools(s, b)` is already called at server.go:88. The new tool is added as an additional `s.AddTool` call **inside** the existing `registerSessionTools` function in sessions.go. Do not touch server.go.

**Naming:** `start_task_agent` — matches the codebase's verb_resource_entity convention (`create_task`, `delete_task`, `move_task`, `open_review`). The orchestrator's suggested name is correct.

## Security Note (privilege change — recorded, accepted)

This tool is a privilege change: an agent can now spawn other agents. The accepted risks, per the user-locked MCP-only decision:

1. **No new auth surface.** The bridge inherits `KAMACU_HOOK_TOKEN` from env (bridge.go:42-55) and sends it as `X-Kamacu-Token` on every call (bridge.go:65). Kamacu's existing receiver gate still applies — only a token-bearing caller (an agent spawned by Kamacu) reaches the API. This tool adds no new auth path; it reuses the same loopback + token posture as every other bridge tool.
2. **Recursive spawn is now possible** (an agent inside a task PTY could call `start_task_agent` for another task). This is acceptable: the agent IS the user's delegate, same as `delete_task` or `open_review` already are. The one-running-agent-per-task dedup (sessions.go:310) still bounds the blast radius per task.
3. **Cost / quota.** Each spawned agent consumes Claude budget. This is the user's delegate acting with their authority — the same trust level as the existing destructive tools. No rate-limiting or throttling is added in this task (explicitly out of scope above).
