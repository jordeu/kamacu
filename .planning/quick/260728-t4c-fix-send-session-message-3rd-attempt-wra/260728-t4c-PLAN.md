# Quick Task 260728-t4c: Bracketed paste wrap for send_session_message

## Objective

This is the third fix to `send_session_message`. The previous two fixes (CR terminator in 260728-s5a, split write in 260728-sm5) were each necessary but not sufficient. Live testing against Claude Code v2.1.22 / Opus 5 confirms the actual root cause and the deterministic fix.

**Root cause:** Raw-mode TUIs (Claude Code via Ink, opencode, anything readline/bubbletea-based with bracketed paste enabled) use a heuristic paste detector on stdin chunks. Programmatic writes from Kamacu arrive at PTY-read speed (microseconds), which is far faster than human typing. The TUI's heuristic fires on essentially any programmatic write regardless of size, treating the chunk as paste content and absorbing any trailing `\r` into the paste buffer rather than interpreting it as the Enter key.

**Verified fix:** Wrap the message body in the ANSI bracketed paste sequence (`ESC[2004<body>ESC[2014`), then write `\r` as a SEPARATE WriteInput call AFTER the closing bracket. The brackets tell the TUI "this is one paste event, here is where it starts and ends" — the heuristic is bypassed because the protocol is explicit. The trailing `\r` lands outside the bracket, so the TUI reads it as a standalone Enter keystroke and submits the captured paste.

### Task 1: Wrap body in bracketed paste markers, keep split write for the trailing CR

**Files:**
- `internal/api/sessions.go` (modify the `input` handler)

**Action:**

Current shape (post-260728-sm5):

```go
msg := req.Message
msg = strings.TrimSuffix(msg, "\n")
msg = strings.TrimSuffix(msg, "\r")
if err := sess.WriteInput([]byte(msg)); err != nil {
    writeError(w, http.StatusConflict, err.Error())
    return

    return

```

New shape — wrap the body in `ESC[2004...ESC[2014` as ONE write (so the TUI sees a single, complete paste event), then `\r` as a SECOND write outside the bracket:

```go
msg := req.Message
// Strip any caller-supplied trailing terminator so we control the submit key.
msg = strings.TrimSuffix(msg, "\n")
msg = strings.TrimSuffix(msg, "\r")

// Wrap the body in ANSI bracketed paste markers (ESC[2004 ... ESC[2014).
// Raw-mode TUIs (Claude Code via Ink, opencode, anything readline-based with
// bracketed paste enabled) use a heuristic paste detector on stdin chunks.
// Programmatic writes arrive at PTY-read speed — far faster than human typing
// — so the heuristic fires on essentially any write, absorbing any trailing
// \\r into the paste buffer as content rather than interpreting it as the
// Enter key. The explicit brackets tell the TUI "this is one paste event,
// here is where it starts and ends", bypassing the heuristic. The trailing
// \\r is written as a SEPARATE call AFTER the closing bracket so the TUI
// reads it as a standalone Enter keystroke and submits the captured paste.
//
// Verified live against Claude Code v2.1.22 / Opus 5: idle agent transitions
// to working within seconds. See quick-task 260728-t4c SUMMARY for the
// reproduction transcript.
const (
    pasteStart = "\x1b[2004" // ESC[2004 — bracketed paste start
    pasteEnd   = "\x1b[2014" // ESC[2014 — bracketed paste end
)
body := pasteStart + msg + pasteEnd
if err := sess.WriteInput([]byte(body)); err != nil {
    writeError(w, http.StatusConflict, err.Error())
    return
}
if err := sess.WriteInput([]byte("\r")); err != nil {
    writeError(w, http.StatusConflict, err.Error())
    return
}
writeJSON(w, http.StatusOK, map[string]int{"bytes_written": len(body) + 1})
```

Also update the comment block above the handler (currently explains CR-vs-LF + split write) to explain the bracketed paste layering: terminator → split write → bracketed wrap. Cite 260728-s5a, 260728-sm5, and 260728-t4c as the iterative diagnosis trail.

**Verify:**

```bash

grep -c 'sess.WriteInput' internal/api/sessions.go   # still TWO calls
grep 'pasteStart\|pasteEnd\|ESC\[2004\|\\x1b\[2004' internal/api/sessions.go   # bracket constants in place
```

**Done:**

Handler wraps body in `ESC[2004...ESC[2014`, writes the wrapped body as ONE call, writes `\r` as a SECOND call. Response reports `len(body) + 11` bytes (5 prefix + body + 5 suffix + 1 CR).

## Out of Scope

- **Per-character typing simulation.** Not needed — the bracketed sequence is deterministic. Per-character would add syscall overhead and is the wrong abstraction (we ARE pasting, not typing).
- **Bracket-escape for messages containing literal `ESC[2004` or `ESC[2014` sequences.** Agent prompts rarely contain literal ANSI sequences; the rare case (an agent prompt about terminal sequences) would have its brackets prematurely closed. Acceptable known limitation; document in the comment block but don't fix.
- **Conditional bracketing based on session kind (agent vs bash).** Always bracket — modern bash with default readline config handles bracketed paste correctly, and the send_session_message tool is scoped to agent sessions in practice (bash tabs don't need it). If a bash-tab case surfaces, add a `kind == KindAgent` check then.
- **Detection of whether the agent has bracketed paste mode enabled.** Adds complexity for a case that doesn't exist in practice — Claude Code and opencode both enable it unconditionally.
- **PROJECT.md / ROADMAP.md doc updates.**
- **MCP tool changes** (`internal/mcp/sessions.go`) — the tool bridges verbatim; the contract is unchanged. Callers continue to send `{"message":"..."}` and the endpoint handles bracketing internally.
