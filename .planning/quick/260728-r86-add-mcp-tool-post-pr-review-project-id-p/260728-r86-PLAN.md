# Quick Task: Add `post_pr_review` MCP tool (v1.3 no-GitHub-writes reversal, agent-delegate surface only)

## Objective

Ship the `post_pr_review(project_id, pr_number, verdict, body?, inline_comments?)`
MCP tool, its backing Kamacu endpoint `POST /api/projects/{id}/pull-requests/{n}/reviews`
(plural — distinct from the singular `/review` open-workspace route), and the
`github.PostReview` helper that shells out to `gh api`. An agent running inside a
Kamacu task PTY can now post a PR review (approve / request-changes / comment,
optionally with inline line comments) to GitHub — the one capability v1.3's
"no GitHub writes" Out-of-Scope rule explicitly prohibited.

The reversal is **MCP-only and additive**: the browser offers no review-posting
UI (zero `web/src/` changes), and the user's existing terminal path
(`gh pr review` / GitHub.com) stays available. The manual-git philosophy is
preserved for the human UX; the MCP delegate is an additional path at the same
trust level as `start_task_agent`, `send_session_message`, `delete_task`, and
`delete_project`.

## Background

**Why v1.3 prohibited GitHub writes, and why it is now reversed only for the MCP surface.**
PROJECT.md's Out-of-Scope section (line 276) states: "Merge/PR *write* automation
from the app (approve/request-changes/comment/merge) — done by the user in the
terminal". The v1.3 Key Decision (line 178) reinforces: "No in-app GitHub write
actions ... done in the terminal, preserving the manual-git philosophy." The
rationale was that the *browser app* should stay a review-surfacing + worktree
tool, not a GitHub-acting tool — keeping the human in the loop via the terminal.

The reversal is scoped and principled, and mirrors the two prior v1.11 reversals
(`start_task_agent` reversing no-auto-start, and `send_session_message` reversing
the D-14 read-only-terminal contract — both MCP-only):
- The **trust boundary is unchanged**: "any agent Kamacu spawned", gated by the
  inherited `KAMACU_HOOK_TOKEN` envelope + loopback binding. A caller without
  the token cannot reach the endpoint.
- The **browser UX is untouched** — zero files under `web/src/` change. The
  browser remains review-surfacing-only; `post_pr_review` is an agent-delegate
  affordance.
- The **terminal path coexists**: the user can still `gh pr review` in a bash
  tab. The MCP delegate is additive, not a replacement.

**The gh CLI is the write path — mirror the v1.3 read path.** The existing
`internal/github` package shells out to `gh` for ALL GitHub access
(`ViewPR`/`PRState` read via `gh pr view`; `ListReviewRequested` via `gh pr list`;
`Clone` via `gh repo clone`). Writes go through the same channel: `gh api
repos/{owner}/{repo}/pulls/{n}/reviews --input -` with the JSON body on stdin.
The GitHub REST endpoint accepts `{"body", "event": "APPROVE"|"REQUEST_CHANGES"|
"COMMENT", "comments":[{"path","line","body"}]}`.

**Mechanical shape — repeat the milestone's bridge pattern, three layers.** The
github helper mirrors `Clone`/`ViewPR` (package-var exec seam + arg-array shell-out).
The API endpoint mirrors the existing `POST .../review` singular handler's
two-gate ladder (pullrequests.go:148-185). The MCP tool mirrors `openReview`
(reviews.go:328-338) but with a marshaled JSON body, delegating to `bridge.call`.

**Correction to the orchestrator example signature:** the brief's example used
`PostReview(ctx, repo RepoRef, prNumber int, event string, ...)`. The sibling
helpers `ViewPR(ctx, repo string, n int)` and `PRState(ctx, repo string, n int)`
take `repo string` (the canonical owner/name), and the API handler already holds
`ghRepo` as a string (from the DB SELECT). For consistency with the sibling
helpers, **`repo string` is used, not `RepoRef`**. And per scope_constraints, the
verdict→event map lives INSIDE PostReview (not at the API layer), so the param is
`verdict string` (the lowercase taxonomy), not `event string`.

## Security Note (acknowledged risk, NOT fixed in this task)

This is a **one-way-door action**: once a review is posted to GitHub, the PR
author gets a notification, CI status may flip (approve dismisses prior
request-changes, etc.), and the review is publicly visible. Three points:

1. The `KAMACU_HOOK_TOKEN` gate is unchanged — same trust boundary as every other
   destructive tool. The reversal adds no new auth surface.
2. **No dry-run mode.** The agent is responsible for asking the user before
   calling this tool (per the user's "ask approval before publishing" workflow
   requirement). The tool itself does NOT prompt — that is the agent's job, in
   its own workflow prompt, before invoking `post_pr_review`.
3. **No content sanitization.** Verbatim passthrough — same as every other bridge
   tool. GitHub's own content filters apply on receipt.

The prompt-injection escalation path (agent reads a malicious tool result →
injected → calls `post_pr_review` to post a hostile review) is a REAL risk and is
**intentionally not mitigated technically here**. The mitigation is the user's
authority model: the user trusts the agent they spawned with the same authority
they themselves have. This is identical to the posture of `start_task_agent`,
`send_session_message`, `delete_task`, and `delete_project`.

            if perr != nil { writeError(w, http.StatusBadRequest, "invalid PR number"); return }

            // GATE 1 (GHSET-02): integration off -> 409, never spawn gh.
            val, err := settings.Get(db, settings.KeyGithubIntegration)
            if err != nil { writeError(w, http.StatusInternalServerError, err.Error()); return }
            if val != "on" { writeError(w, http.StatusConflict, "GitHub integration is off"); return }

            // GATE 2: project not linked / unknown -> 409, never spawn gh.
            var repo sql.NullString
            qerr := db.QueryRow(`SELECT github_repo FROM projects WHERE id = ?`, pid).Scan(&repo)
            if errors.Is(qerr, sql.ErrNoRows) { writeError(w, http.StatusConflict, "project is not linked to a GitHub repo"); return }
            if qerr != nil { writeError(w, http.StatusInternalServerError, qerr.Error()); return }
            if !repo.Valid || strings.TrimSpace(repo.String) == "" {
                writeError(w, http.StatusConflict, "project is not linked to a GitHub repo"); return
            }

            // Decode the request body.
            var req struct {
                Verdict        string `json:"verdict"`
                Body           string `json:"body"`
                InlineComments []struct {
                    Path string `json:"path"`
                    Line int    `json:"line"`
                    Body string `json:"body"`
                } `json:"inline_comments"`
            }
            if derr := json.NewDecoder(r.Body).Decode(&req); derr != nil {
                writeError(w, http.StatusBadRequest, "invalid JSON body"); return
            }

            // Map to the github.InlineComment shape + call PostReview (which owns
            // the verdict→event taxonomy + the gh spawn).
            comments := make([]github.InlineComment, len(req.InlineComments))
            for i, c := range req.InlineComments {
                comments[i] = github.InlineComment{Path: c.Path, Line: c.Line, Body: c.Body}
            }
            out, perr := postReview(r.Context(), repo.String, int(n), req.Verdict, req.Body, comments)
            if perr != nil {
                msg := perr.Error()
                if strings.HasPrefix(msg, "unknown verdict") {
                    writeError(w, http.StatusBadRequest, msg) // 400 on a bad verdict
                    return
                }
                writeError(w, http.StatusBadGateway, "couldn't post this review: "+msg) // 502 on gh failure
                return
            }

            // 201 Created with the gh JSON response verbatim.
            w.Header().Set("Content-Type", "application/json")
            w.WriteHeader(http.StatusCreated)
            _, _ = w.Write(out)
        })

## Out of Scope

These pieces of the user's described workflow ("/review PR #<n> and use subagents
to double-check findings and assess importance, give a final verdict, ask approval
before publishing") belong in the **agent's workflow prompt**, NOT in the MCP
server. The MCP tool delivers ONLY the publishing primitive.

1. **Multi-agent orchestration** (subagents double-checking findings, assessing
   importance) — the agent calling `post_pr_review` uses its OWN Task-tool /
   subagent mechanism (e.g. Claude Code's Task tool, opencode's equivalent). The
   MCP server does not spawn or coordinate subagents. Verdict synthesis (deciding
   approve vs. comment) happens in the agent's workflow prompt; the MCP tool just
   takes the verdict string as input.

2. **Publish-checkpoint UX** ("ask approval before publishing") — the agent's
   workflow prompt uses its own ask-user mechanism BEFORE calling `post_pr_review`.
   The MCP tool posts immediately when called; it does NOT prompt. No dry-run mode
   is added (see Security Note).

3. **Rate limiting / abuse protection** — same trust model as `start_task_agent`
   and `send_session_message`: the agent is the user's delegate. No send-quotas,
   no inter-agent permission prompts, no cooldowns.

4. **Fetching the diff for review** — out of scope. The agent uses existing tools
   (`open_review` to get a worktree, or the existing gh-backed read surface via the
   browser) to read the diff. If a future `get_pr_diff` MCP tool is needed, that is
   a separate quick task.

5. **Browser review-posting UI** — ZERO files under `web/src/` change. The browser
   remains review-surfacing-only (the manual-git philosophy stays intact for the
   human). The terminal path (`gh pr review` / GitHub.com) coexists unchanged.

Additional inherited out-of-scope items:
- **Content sanitization / quoting / escaping** — verbatim passthrough. GitHub's
  own content filters apply on receipt.
- **PROJECT.md / STATE.md doc edits** — the v1.3 Out-of-Scope line evolution
  (MCP-only reversal of the no-writes rule) is the orchestrator's separate concern,
  handled post-task. This plan does not edit PROJECT.md.
- **Typed bridge error taxonomy / stdout guards / e2e harness (MCPHARD)** —
  inherited Out-of-Scope from v1.11, unchanged. This tool surfaces generic MCP
  errors via the Phase 07 D-05 wrap.
- **`internal/mcp/server.go`** — NOT modified. `registerReviewTools` is already
  wired at server.go:89; the new tool is added inside that function.
