# Summary: Add `post_pr_review` MCP tool (v1.3 no-GitHub-writes reversal, agent-delegate surface only)

## Abstract

Shipped the `post_pr_review(project_id, pr_number, verdict, body?, inline_comments?)`
MCP tool, its backing Kamacu endpoint `POST /api/projects/{id}/pull-requests/{n}/reviews`
(PLURAL — distinct from the singular `/review` open-workspace route), and the
`github.PostReview` helper that shells out to `gh api repos/{owner}/{repo}/pulls/{n}/reviews
--input -`. An agent running inside a Kamacu task PTY can now post a PR review
(approve / request-changes / comment, optionally with inline line comments) to
GitHub — the one capability v1.3's "no GitHub writes" Out-of-Scope rule
explicitly prohibited.

The reversal is **MCP-only and additive**: zero `web/src/` changes (the browser
offers no review-posting UI), and the user's existing terminal path
(`gh pr review` / GitHub.com) stays available. The trust boundary
(`KAMACU_HOOK_TOKEN` + loopback) is unchanged — same gate as
`start_task_agent`, `send_session_message`, `delete_task`, `delete_project`.

## Layer-by-layer

### 1. `internal/github/review.go` — the WRITE seam

`PostReview(ctx, repo string, prNumber int, verdict, body string, comments []InlineComment) ([]byte, error)`

- Validates the verdict (`approve`/`request_changes`/`comment`) BEFORE any gh
  spawn — unknown verdict → `(nil, error)` without touching `Available()` or
  the runner.
- Maps the verdict to GitHub's `APPROVE`/`REQUEST_CHANGES`/`COMMENT` via
  `verdictToEvent` — the taxonomy lives in exactly one place (this package).
- Marshals `{event, body?, comments?}` with `omitempty`-style conditional map
  keys (an absent body and nil comments produce a payload without those keys).
- Delegates to `postReviewRunner` (the package-level exec seam, mirroring
  `cloneRunner`); tests swap the seam so the SUCCESS path is also stub-driven
  (posting needs live GitHub, unlike Clone which has a file:// fallback).
- `realPostReview` shells out to `gh api repos/{repo}/pulls/{n}/reviews --input -`
  with an **arg array** (never `sh -c` — repo is attacker-adjacent input); only
  the marshaled JSON body crosses stdin. Available-guarded; nonzero exit
  surfaces as an error carrying the trimmed stderr (a leading `fatal: ` stripped,
  mirroring Clone).

### 2. `internal/api/pullrequests.go` — the PLURAL endpoint

`POST /api/projects/{id}/pull-requests/{n}/reviews`

- Registered as a NEW route inside `PullRequestRoutes`, distinct from the
  singular `/review` open-workspace route (the existing handlers are
  byte-for-byte unchanged).
- Runs the SAME two-gate ladder as `/review`:
  - GATE 1 (settings toggle off) → 409 `"GitHub integration is off"`.
  - GATE 2 (NULL/empty `github_repo`, unknown project) → 409 `"project is not
    linked to a GitHub repo"`.
- The gate SELECT fetches ONLY `github_repo` (no `repo_path`) — the plural
  route does NOT provision a worktree (mirrors the GET detail handler at :117,
  not the singular `/review` worktree-provisioning route).
- Decodes `{verdict, body, inline_comments:[{path,line,body}]}`, maps to
  `github.InlineComment`, calls `postReview` (the swappable seam, mirroring
  `viewPR`).
- Response shape:
  - 201 Created with the gh JSON response verbatim (`Content-Type:
    application/json`, raw `[]byte` write).
  - 400 on an unknown verdict (PostReview's error message starts with
    `"unknown verdict"` — prefix-sniffed and mapped to 400).
  - 400 on a malformed JSON body (`"invalid JSON body"`).
  - 400 on a non-numeric `{n}` (`"invalid PR number"`).
  - 502 on a gh failure (`"couldn't post this review: <err>"` — mirrors the
    existing 502 degrade shape at pullrequests.go:207/246).

### 3. `internal/mcp/reviews.go` — the delegate tool

`post_pr_review` is registered as the FOURTH `s.AddTool` block inside
`registerReviewTools` (alongside `list_pending_reviews` /
`list_recently_reviewed` / `open_review`).

- InputSchema: `project_id` (integer, required), `pr_number` (integer,
  required), `verdict` (string, required, enum
  `[approve, request_changes, comment]`), `body` (string, optional),
  `inline_comments` (array of `{path, line, body}`, optional).
- The Description flags this as a **one-way-door action** and tells the agent
  to ask the user for approval BEFORE calling — the tool itself does NOT
  prompt (the agent's workflow prompt owns the publish-checkpoint UX).
- `postPRReview` handler performs **NO validation, NO content sanitization, NO
  verdict mapping, NO dry-run** — verbatim passthrough. The verdict taxonomy +
  gh spawn live server-side (PostReview owns them).
- Marshals `{verdict, body?, inline_comments?}` with the same conditional-map
  pattern as the API layer (omitted optional fields never reach Kamacu).
- Delegates to `b.call(ctx, POST, "/api/projects/%d/pull-requests/%d/reviews",
  bytes.NewReader(jb))` — the locked D-05 2xx→passthrough / non-2xx→wrap
  contract.
- NOT wrapped in `withRecover` — matches the `reviews.go` file convention
  (Phase 09 SUMMARY: reviews.go did NOT adopt withRecover; sessions.go did).
- `internal/mcp/server.go` is NOT modified — `registerReviewTools` was already
  wired at server.go:89.

## Security note (acknowledged, not fixed in this task)

This is a **one-way-door action**: once posted, the PR author is notified, CI
status may flip, and the review is publicly visible. The trust boundary
(`KAMACU_HOOK_TOKEN` + loopback) is unchanged — same gate as every other
destructive tool. The reversal adds no new auth surface.

No dry-run mode, no content sanitization, no rate limiting — the agent is the
user's delegate, with the same authority the user has. The publish-checkpoint
("ask approval before publishing") lives in the **agent's workflow prompt**,
NOT in the MCP server; the tool posts immediately when called.

The prompt-injection escalation path (agent reads a malicious tool result →
injected → calls `post_pr_review` to post a hostile review) is a REAL risk and
is intentionally not mitigated technically here. The mitigation is the user's
authority model — identical to the posture of `start_task_agent`,
`send_session_message`, `delete_task`, `delete_project`.
