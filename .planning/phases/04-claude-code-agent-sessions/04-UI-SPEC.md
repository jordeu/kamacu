# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Sources: 04-CONTEXT.md decisions D-35..D-53 (locked), Phase 1 UI-SPEC (approved — design system foundation; its Color section explicitly reserved the status-badge palette for this phase), Phase 2 UI-SPEC (approved — TerminalPane contract carries forward verbatim), Phase 3 UI-SPEC (approved — tab strip, no-worktree states, cleanup dialogs), existing code (`TaskTabs.tsx` TabDef seam, `TaskCard.tsx` CardShell, `ProjectSidebar.tsx` menu rows, `TerminalPane.tsx` header/banner anatomy). Claude's discretion areas (exact dot styling within the color budget, status-latency expectations, agent label) resolved below. No user questions were needed.

**Scope note:** This contract EXTENDS Phases 1–3; it never redefines them. Terminal internals (xterm theme, connection banners, replay/resize, Stop semantics) are the Phase 2 contract, untouched. Tab strip mechanics, cleanup dialogs, and worktree presence surfaces are the Phase 3 contract, untouched — except where D-42 folds the agent session into existing session counts (copy unchanged, counts include the agent). This phase ADDS: (1) **the status palette** — the new semantic color family Phases 1–3 held the budget for, (2) the permanent Agent tab with pre-start / running / exited states, (3) status dots on cards and the Agent tab label, (4) the waiting treatment (pulse + card border), (5) the sidebar waiting-count chip, (6) the `Insert description` pane-header action.

## Color

Inherited Phase 1 budget unchanged: dominant zinc-950 `#09090b`, secondary zinc-900 `#18181b` surfaces / zinc-800 `#27272a` borders, accent blue-500 `#3b82f6`, destructive red-500 `#ef4444`. ### Status palette (NEW — this is the moment the budget was reserved for)

The status palette is a semantic family, not decoration. It may appear in **exactly three surfaces** and nowhere else:

1. **Status dots** — task card, Agent tab label
2. **Waiting card border** — the D-44 highlight
3. **Sidebar waiting-count chip** — D-49

| Status (D-43) | Color | Hex | Contrast on zinc-900 card | Treatment |
|---------------|-------|-----|---------------------------|-----------|
| working | green-500 | `#22c55e` | ~6.9:1 ✓ | solid dot |
| waiting for input | amber-400 | `#fbbf24` | ~10:1 ✓ (loudest hue — intentional) | dot pulses + card border highlight (D-44) |
| idle | zinc-400 | `#a1a1aa` | ~7:1 ✓ | solid dot (same ramp value as muted text — idle is calm by design) |
| exited (code 0) | zinc-600 | `#52525b` | ~2.4:1 — **declared exception**: deliberately muted; a cleanly finished agent is the de-emphasized state, tooltip carries the detail | solid dot |
| exited (non-zero) | red-500 | `#ef4444` | ~4.5:1 ✓ | solid dot |
| no agent session ever / pre-start | — | — | — | **no dot rendered** (absence means "no agent") |

Rules:

- **Dot size:** 8px (`size-2`), `rounded-full`, no border/ring around the dot itself. One `StatusDot` component reused on card and tab.
- **Pulse (waiting only):** Tailwind built-in `animate-pulse` (2s opacity 1→0.5 ease-in-out infinite) on the amber dot — motion-restrained, no ping halo, no scale animation. Guard with `motion-reduce:animate-none`; under reduced motion the card border highlight remains the loud signal.
- **Waiting card border (D-44):** the card's 1px zinc-800 border becomes 1px amber-400 at 40% opacity (`border-amber-400/40`). Subtle — the border changes hue, nothing else about the card changes. Hover still lightens the surface one step (Phase 1 rule); the border stays amber while waiting.
- **Sidebar chip (D-49):** amber-400 `#fbbf24` text on amber-400/10 background (`bg-amber-400/10`), rounded-full, 12px/500 tabular-nums, 4px horizontal padding, 18px min-width, centered count. Static — the chip never pulses (one pulsing element per surface; the dots own motion).
- **Red-500 budget extension:** red-500 (Phase 1: destructive actions only) gains exactly one additional use — the exited-with-error status dot. It remains forbidden everywhere else outside destructive confirmations and the existing ghost-destructive Stop.
- **Explicitly NOT status-colored:** the `Start agent` button (standard inverted primary, never green), banners (zinc-900, Phase 2), tab labels and any text (status is never communicated by colored text — dot + tooltip only), terminal chrome, board column headers, the Agent tab active indicator (stays accent blue-500, reservation #2).

Accent blue-500 reserved for (unchanged from Phase 1): focus-visible rings, active tab indicator, drag-over column, prose links. This phase adds **no** new accent uses — the Agent tab gets the existing active-tab indicator for free.

## Interaction Contract

States the executor must implement; the auditor will check these.

### Agent tab lifecycle

| Interaction | Contract |
|-------------|----------|
| Tab order (D-38) | `Agent` first (always), then `Description`, then `Bash 1..N`, then the `+` button. Agent never renders a ×; it cannot be closed, only stopped |
| Landing tab (D-39) | Opening a task always activates the Agent tab — no smart selection. (Supersedes Phase 3's "default active tab is Description") |
| Start (D-40) | Click `Start agent` → POST spawn (cwd = worktree, kind = agent, exactly one agent per task enforced server-side) → pane attaches in place (pre-start block swaps to TerminalPane). Button disabled `Starting…` while in flight |
| Insert description (D-35/D-36) | Click `Insert description` → the task description is typed into the prompt via bracketed paste — **never submitted**, editable before sending, repeatable. Available whenever the session is running; hidden when the description is empty |
| Stop / exit (D-41) | Standard Phase 2 teardown UX. On exit (stop or self-exit): exited banner with `Start again`; clicking it spawns a fresh claude session in the same pane (no --resume this phase). Terminal output stays frozen, readable, copyable (D-15) until the fresh session replaces it |
| Reattach (TERM-05 / SC-4) | Reopening a task with a running agent reattaches with a correctly redrawn claude TUI — brief replay flicker acceptable, corrupted alt-screen is not (mechanism is backend discretion; this is the user-visible bar) |
| Cleanup gate (D-42) | The agent session counts and is stopped exactly like bash sessions; after cleanup the Agent tab shows the pre-start no-worktree state |
| Keep-mounted | The Agent tab content uses the existing `keepMounted` TabDef path — switching tabs never detaches the agent WS |

### Status dots

| Interaction | Contract |
|-------------|----------|
| Card dot (D-43, D-48) | Reflects the AGENT session only — bash sessions never drive it. No agent session ever started → no dot. Exited dot persists until a new agent session starts for that task |
| Tab dot (D-50) | The same `StatusDot` (same state source) renders left of the `Agent` tab label, xs gap — visible while on Description/bash tabs. No dot pre-start |
| Waiting treatment (D-44) | Amber dot pulses (`animate-pulse`, `motion-reduce:animate-none`) on card AND tab; the card additionally gets the amber-400/40 border. Everything else is calm — working/idle/exited never animate |
| Waiting clears on attach (D-45) | Opening the task's Agent tab (WS attach) clears waiting; the open client reflects the change immediately (optimistic), other surfaces on the next status update. Re-fires if Claude prompts again |
| Stop hook → idle (D-46) | Claude finishing a turn while the session stays open shows the gray idle dot — there is no "done" state, no celebratory color |
| Status latency | Waiting must surface on board and sidebar within 5s of the hook event (one existing poll period; push is permitted but not required — discretion). Tooltips always reflect the rendered dot, never a fresher state |
| Tooltips | Dots are wrapped in a tooltip trigger span; dots themselves are non-interactive and never intercept card click/drag (`pointer-events` on the wrapper only for hover) |

### Sidebar chip

| Interaction | Contract |
|-------------|----------|
| Visibility (D-49) | Rendered on a project row only when that project has ≥1 agent in waiting; disappears at zero. Counts agents, not tasks-with-sessions |
| Placement | Right-aligned inside the `SidebarMenuButton` row, before the row's `ProjectMenu` affordance; project name truncates to make room |
| Behavior | Not independently clickable — the row's existing navigation is the action. No pulse |

Focal point: on the pre-start Agent tab, `Start agent` is the only inverted high-contrast element. On the board, amber waiting dots are the loudest elements by design — nothing else may compete (which is why the rest of the palette stays neutral).
