<objective>
Close three code-review findings in `internal/migrate/paths.go` (source: `21-REVIEW.md`) that undermine the
phase's core guarantee — worktrees stay valid across the `~/.kangent` → `~/.kamacu` move for ALL project
types, with no data loss:

- **CR-01 (CRITICAL):** `repairWorktrees` selects `WHERE managed=1` only, but `provisionWorktree`
  (`internal/api/tasks.go:120`, via `worktree.PathUnder(worktree_base, …)`) places task worktrees under the
  global `worktree_base` (`~/.kangent/worktrees/…`) for EVERY project regardless of `managed` — the flag gates
  only a best-effort fetch, never placement. So a folder-pointed (managed=0) project — whose main repo lives
  OUTSIDE the data root and does not move — still has task worktrees under the moved root. `rewriteManagedPaths`
  rewrites those tasks' `worktree_path` to the new root (correct — the tasks query is NOT managed-filtered), but
  repair SKIPS the managed=0 project, so the external repo's `.git/worktrees/<id>/gitdir` stays pointed at the
  vanished old path. A later `worktree.Remove` runs `git worktree prune` (`worktree.go:378`), which deregisters
  that stale worktree → sibling worktree loss (orphaned live checkouts holding uncommitted agent work), with
  the DB already pointing at the just-deregistered path — a silent integrity break in the milestone's
  highest-risk phase, and untested.
- **WR-01 (WARNING):** the LIKE gate `OldRoot||'/%'` is unescaped, so a `_`/`%` in `OldRoot` (legal in a Unix
  home, e.g. `/home/john_doe/.kangent`) over-matches a non-prefixed row; `rewritePrefixColumn` then writes a
  corrupted `filepath.Join(NewRoot, <whole absolute oldPath>)` value.
- **WR-02 (WARNING):** `rewriteWorktreeBaseSetting` uses `strings.HasPrefix` without a separator boundary, so a
  `worktree_base` of `~/.kangent-backup/…` (a dir OUTSIDE the migrated root) is mis-rewritten to
  `~/.kamacu-backup/…`.

Fix, TDD (RED regression test first, then GREEN): broaden repair to every repo owning a migrated (under-new-root)
worktree, gated on under-root worktree ownership rather than the managed flag, keeping the 21-06 per-path
log+skip tolerance; and add Go-side prefix-boundary rechecks to the LIKE-gated rewrites and a separator boundary
to the worktree_base rewrite.

Coverage (findings → tasks): CR-01 → Task 1; WR-01 + WR-02 → Task 2. MIGRATE-02/03 re-covered.
Out of scope (deferred, optional per review — NOT closed here to keep the plan tight): WR-03
(frontend `migrateStorage.ts` index-mutation), IN-01 (repair ctx timeout), IN-02 (symlinked data root).

Purpose: no first-class project class (folder-pointed repos) silently loses worktrees to the migration, and the
path rewrite can never corrupt a path outside the moved root.
Output: a broadened, boundary-checked `internal/migrate/paths.go` with git-integration + no-git regression tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git-CLI invocation on managed AND unmanaged repos | `git worktree repair`/`prune` now runs against folder-pointed EXTERNAL repos too; a mis-scoped repair could touch a repo/worktree outside the migration's intent |
| DB path values ← SQLite LIKE gate | `OldRoot`/`NewRoot` reach a `LIKE` pattern; unescaped `_`/`%` metacharacters in a home path can over-match and drive a corrupted `filepath.Join` UPDATE |
| worktree_base setting value | a user-set value may point at a SIBLING of the data root (`~/.kangent-backup`); an unbounded prefix match rewrites it out from under the user |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-21-08-01 | Tampering (worktree loss) | `repairWorktrees` skipping folder-pointed repos → stale gitdir deregistered by later `git worktree prune` | mitigate | Broaden repair to every project owning a migrated worktree, run from each project's own `repo_path`, gated by under-new-root worktree ownership (not the managed flag); regression test asserts the migrated worktree survives a subsequent prune |
