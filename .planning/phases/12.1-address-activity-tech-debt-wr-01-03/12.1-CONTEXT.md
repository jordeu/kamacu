## Phase Boundary

It hardens three Phase 11 Activity-page artifacts against non-blocking quality defects the milestone audit (and `11-REVIEW.md`) documented. **No backend, no SQL, no migration, no new API, no new dependency.** The fixes are surgical edits to existing React hooks/components.

Delivers:
1. **WR-01/04 — wire the `useActivity` `enabled` gate** so first-time users (no saved scope) don't fire a wasted `global` fetch that is immediately discarded when the default-promotion effect flips scope to `workspace:<id>`, and don't see a brief wrong-scope flash on first open. (The `enabled` parameter already exists at `queries.ts:95-107` with a default of `true`; the sole caller `ActivityPage.tsx:24` never passes it — the documented Pitfall 6 mitigation is dead in practice. This phase makes it live.)
2. **WR-02 — resolve a stale/deleted persisted scope to its real effective value** instead of labeling it "Global" while still querying the dead id. 3. **WR-03 (a11y) — restore the PR title to the `ReviewsList` external link's accessible name.** Today `aria-label="Open PR #42 on GitHub"` *replaces* the visible text (`#42 Title <time>`) as the accessible name, so screen readers hear only "Open PR #42 on GitHub" — never the title that distinguishes entries. ## Implementation Decisions

> The user deferred all four gray areas to the recommended option. The decisions below are the recommended defaults, locked.

### WR-01 — gate strategy (wire the `enabled` gate)

- **D-01: Wire the gate — do NOT delete the parameter.** The `enabled` parameter was a deliberately-designed Pitfall 6 mitigation documented in four Phase 11 planning artifacts (`11-RESEARCH.md:400`, `11-PATTERNS.md:648`, `11-01-PLAN.md:93`, `11-UI-SPEC.md:165`). The implementation simply omitted it. Wiring it honors the documented contract AND eliminates a real user-visible wart (the brief wrong-scope flash + wasted fetch on first open), not just a code-smell. Deleting the parameter (the audit's alternative) would codify "the mitigation we designed isn't worth it" — wrong call for a one-line wiring that fixes a real first-run UX defect.
- **D-02: "Settled" semantics.** Expose a `scopeResolved` flag from `useActivityView` and pass it as the `enabled` arg in `ActivityPage`. **Settled = (a persisted scope exists in `localStorage`) OR (`activeWorkspaceId` has resolved to non-`null`).** This handles both paths:
  - **Returning user with a saved scope** → resolved `true` on first render (no flash, no wasted fetch — the saved scope is used directly).
  - **First-time user (no saved scope)** → resolved `true` once `activeWorkspaceId` is non-`null`, so the fetch fires *with* the promoted `workspace:<id>` scope (the promotion effect and the gate trip together — no transient `global` fetch, no wrong-scope flash).
  - The flag is `false` only during the brief window where there is no saved scope AND `useWorkspaces()` is still loading. This exactly mirrors the audit's suggested snippet (`11-REVIEW.md` WR-01 Fix).
- **D-03: The gate lives in `useActivityView`, not `ActivityPage`.** `useActivityView` already owns the promotion effect that adopts `workspace:<id>`; the `scopeResolved` flag is the natural complement (it reports whether that effect's inputs have settled). `ActivityPage` consumes `{ scope, setScope, window, setWindow, scopeResolved }` and forwards `scopeResolved` as the third arg to `useActivity(scope, window, scopeResolved)`. The `enabled: boolean = true` default in `queries.ts` stays (keeps the query reusable / testable in isolation).

### WR-02 — stale-scope handling (auto-demote to `global` as the VALUE, centralized)

- **D-04: Resolve a stale/deleted scope against live rows and fall back to `global` as the effective scope VALUE — not just the label.** When a saved `workspace:N`/`project:N` references an id absent from the loaded `useWorkspaces()`/`useProjects()` rows, the *effective* scope becomes `global`: the trigger label reads "Global", the query fetches `?scope=global`, and the "All activity" dropdown item is checked. Label, query, and selection all agree. (This is the audit's primary fix; the "honest label" alternative is rejected — it leaves the query fetching empty data for a dead id with no item checked, which is worse UX than a clean self-heal.)
- **D-05: Centralize the validation in `useActivityView`** — NOT in `ScopeSelector`. `useActivityView` owns the `scope` state; that is the only place a value-level demotion can take effect across the label (`ScopeSelector`), the query (`useActivity`), and the dropdown-check (`ScopeSelector`). `useActivityView` therefore gains reads of `useWorkspaces()`/`useProjects()` to validate the id (it already reads `useActiveWorkspace`; adding the two row queries is consistent). `ScopeSelector`'s `useDisplayName` continues to resolve the label from the (now-validated) effective scope, so it no longer needs its own stale fallback to "Global" for a value that `useActivityView` already demoted.
- **D-06: Mirror `useActiveWorkspace` — do NOT persist the demotion.** The runtime effective scope falls back to `global`, but the saved `localStorage` value is left untouched (the demotion is ephemeral, re-derived each load). This matches `useActiveWorkspace.tsx:57-66`, which keeps `savedId` as-is and recomputes the effective id each render via `useMemo`, persisting only on an explicit `setActiveWorkspaceId`. Rationale: the saved preference is already dangling (it points at something deleted), so falling back loses nothing valid; but overwriting `localStorage` would be a silent destructive change to the user's last pick, and a future re-create of the id (impossible for workspaces today, but conceptually) would not self-restore. The user's next explicit pick overwrites the saved value as normal. The audit's framing of "silently changes a saved preference" is therefore about runtime behavior, not persistence — and a dangling pref is correctly recovered-from, not honored.
- **D-07: Validation granularity = grammar-already-done + liveness-new.** `useActivityView.readScope` already validates the *grammar* (`global | workspace:N | project:N`). This phase adds a **liveness** check layered on top: once `useWorkspaces()`/`useProjects()` rows have loaded, a `workspace:N`/`project:N` whose `N` matches no row id is demoted to `global`. While the row queries are still loading, a grammatically-valid saved scope is used as-is (no premature demotion); the demotion kicks in once rows arrive and the id isn't found. `global` itself is always live (no row lookup).

### WR-03 — a11y fix shape (include the title in the aria-label)

- **D-08: Include the PR title in the `aria-label` — keep the existing aria-label pattern.** The link becomes `aria-label={`Open PR #${review.number} ${review.title} on GitHub`}`. This is the minimal surgical fix that directly closes the flagged defect: screen readers now hear the title. Rationale for choosing this over "drop aria-label, let visible text be the name + visually-hidden 'opens in new tab'":
  - Smaller diff, lower regression risk for a tech-debt phase.
  - Preserves the "on GitHub" external-link cue *inside* the accessible name without reconstructing it as a visually-hidden span.
  - The visible text (`#42 Title <time>`) is unchanged for sighted users.
- **D-09: Exclude the timestamp from the accessible name.** The visible `formatDateTime(review.completedAt)` stays as visible text but is NOT added to the aria-label. It is secondary information, already visible, and a spoken timestamp per entry adds screen-reader verbosity without aiding identification (the `#number + title` is the identity). Including it would lengthen every review announcement.
- **D-10: Do NOT validate the `href` scheme here.** IN-02 (`ReviewsList` `href={review.url}` scheme validation) is a separate security-hardening item outside the WR-01..03 boundary. The URL is constructed server-side from gh data (`internal/github/prlist.go`, `https://github.com/…` form) on a local-only single-user app; defense-in-depth scheme assertion is a real but separate concern. Leave it deferred.

### Verification approach

- **D-11: Verify via the codebase norm — `tsc -b && vite build` + UAT. No new RTL/JSDOM component test harness for this phase.** The `web/` dir has almost no component unit tests (Phase 11/12 verified via UAT + typecheck/build); standing up a harness for three small surgical edits is not warranted. Behavioral UAT covers all three fixes:
  - **WR-01:** clear `kamacu.activity.scope`, open Activity fresh → no Global flash, no discarded fetch (devtools network shows one `?scope=workspace:<id>` call, not a preceding `?scope=global`).
  - **WR-02:** set `kamacu.activity.scope=workspace:<dead-id>`, open Activity → trigger label "Global", "All activity" checked, data is global. Set a dead `project:N` likewise.
  - **WR-03:** reviews list — inspect/announce an entry → accessible name includes the title (axe or screen-reader spot-check).
- **D-12: Optional unit test IF a pure helper is extracted.** If the planner extracts WR-02's liveness check into a pure `resolveEffectiveScope(scope, workspaces, projects)` (rows-loaded → demote-or-pass), a vitest unit test for THAT pure function is encouraged (it's the logic-heavy heart and trivially testable without React). This is optional, not a gate; do not extract purely to make it testable if the inline hook form is cleaner.

### the agent's Discretion

- **How `scopeResolved` is computed in `useActivityView`** — a `useState(() => localStorage.getItem(ACTIVITY_SCOPE_KEY) !== null)` seeded once + an effect that flips it true when `activeWorkspaceId !== null` (the audit's snippet), vs. a `useMemo` deriving it each render from `(hasSavedScope || activeWorkspaceId !== null)`. Either is correct; the `useMemo` form avoids a state+effect pair and re-derives cleanly. Agent picks the cleaner React idiom.
- **Where WR-02's liveness check lives structurally** — a `useMemo` over `(scope, workspaces, projects)` returning the effective scope (mirroring `useActiveWorkspace`'s `useMemo` shape), vs. an effect that calls `setScopeState("global")` on staleness. The `useMemo`-derive-effective form is preferred (D-06: don't persist the demotion → don't `setScopeState`, which would also fire the `setScope` writer path). But if the hook's existing `setScopeState` is purely in-memory state (it is — only the explicit `setScope` wrapper writes localStorage), an effect is also viable. Agent picks; the constraint is: **the demotion must NOT write `localStorage`** (D-06).
- **Whether WR-02's refactor naturally dedupes IN-03** — if centralizing validation in `useActivityView` makes `ScopeSelector`'s double `useWorkspaces`/`useProjects` collapse (e.g. the resolved name flows in as a prop), great — fold it in opportunistically. If not, leave IN-03 as-is (out of scope). Do NOT add work to chase IN-03.
- **Exact aria-label wording** — `Open PR #${number} ${title} on GitHub` is the contract; minor phrasing (e.g. `PR #${number}: ${title} — open on GitHub`) is fine as long as it contains the number AND the title AND signals external/GitHub.
- **Scope of `scopeResolved` interaction with WR-02** — if a returning user has a *stale* saved scope, `scopeResolved` is true immediately (saved scope exists) so the fetch may fire once for the stale id before rows load and demote it. This is acceptable (one loopback GET of empty data, then the correct global fetch) and matches how `useActiveWorkspace` resolves. The agent MAY tighten this (gate `scopeResolved` on liveness too) if cheap, but it is not required.

- **`useActivityView` (`web/src/lib/useActivityView.ts`)** — owns `scope`/`window` state + the promotion effect. - **Resolve-against-live-rows, fall back, don't persist the fallback** — `useActiveWorkspace` does exactly this for workspace ids; WR-02 applies the same discipline to Activity scope (fall back to `global`).

- **Grammar validation on read, layered liveness validation once rows load** — `readScope` already does grammar; WR-02 adds liveness as a second layer (D-07).
- **aria-label as the accessible name replaces visible text** (WAI-ARIA) — the root cause of WR-03; the fix keeps aria-label but makes it carry the title.

### Integration Points
- **`useActivityView` return shape widens** — `{ scope, setScope, window, setWindow }` → adds `scopeResolved` (WR-01). The effective `scope` it returns becomes the demote-to-global value (WR-02) — transparent to callers; `ActivityPage` and `ScopeSelector` consume the already-resolved scope.

## Specific Ideas

- **The user deferred all four gray areas to the recommended option** ("none of them, choose recommended options"). The decisions D-01..D-12 are the recommended defaults, locked without further discussion. No additional specific preferences were expressed.
- **WR-01's gate is the highest-leverage fix.** It's the only one of the three with a user-visible symptom (first-open wrong-scope flash + a wasted fetch), not just a code-quality issue.
