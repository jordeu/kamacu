<interfaces>
API contract (RESEARCH.md Pattern 4 — the frontend in plans 01-03..01-06 is coded against exactly this; do not deviate):

| Method & Path | Body | Returns |
|---------------|------|---------|
| GET /api/projects | — | 200 [Project] |
| POST /api/projects | {name?, repo_path} | 201 Project; 400 invalid path; 409 duplicate |
| PATCH /api/projects/{id} | {name} | 200 Project; 400 empty name; 404 |
| DELETE /api/projects/{id} | — | 204 (CASCADE removes tasks; repo on disk untouched) |
| GET /api/projects/{id}/tasks | — | 200 [Task] ordered by status, position ASC |
| POST /api/projects/{id}/tasks | {title, description?} | 201 Task (status=todo, top of column) |
| GET /api/tasks/{id} | — | 200 Task; 404 |
| PATCH /api/tasks/{id} | {title?, description?} | 200 Task |
| POST /api/tasks/{id}/move | {status, after_id: number|null} | 200 Task |
| DELETE /api/tasks/{id} | — | 204 (hard delete, D-11) |

JSON shapes (snake_case keys; position included so the client can sort but never writes it):

```json
Project: {"id":1,"name":"kangent","repo_path":"/abs/path","created_at":"...","updated_at":"..."}
Task: {"id":1,"project_id":1,"title":"t","description":"","status":"todo","position":1.0,"created_at":"...","updated_at":"..."}
```

Errors: every non-2xx is `{"error":"human-readable message"}`. Exact validation messages (UI-SPEC mirrors them verbatim in the UI): `path must be absolute`, `not a directory: {path}`, `not a git repository: {path}`, duplicate project → 409 with `this repository is already added`.

    Add to `internal/api/tasks.go` the `move` handler for `POST /api/tasks/{id}/move`, body `{"status": string, "after_id": *int64}`:

    Single transaction (`db.BeginTx` — DSN `_txlock=immediate` makes it a write lock), implementing RESEARCH.md Pattern 6:
    1. Load the task by id (404 if missing). Validate `status` against validStatuses → 400 `invalid status`.
    2. If `after_id == nil`: `pos = COALESCE((SELECT MIN(position) FROM tasks WHERE project_id=? AND status=?), 2.0) - 1.0`. Exclude the moving task itself from the MIN scan (`AND id != ?`) so re-dropping at top of its own column works.
    3. If `after_id != nil`: SELECT the after task; it must exist, share project_id with the moving task, AND already have the target status → else 400 `invalid after_id`. `next = SELECT MIN(position) FROM tasks WHERE project_id=? AND status=? AND position > after.position AND id != movingID`. If next is NULL → `pos = after.position + 1.0`, else `pos = (after.position + next) / 2`.
    4. Renormalization guard: if next exists and `next - after.position < 1e-9`, renumber the whole target column inside the same tx: SELECT ids ordered by position, UPDATE each to 1.0, 2.0, 3.0... then recompute pos from the fresh values.
    5. `UPDATE tasks SET status=?, position=?, updated_at=strftime('%Y-%m-%dT%H:%M:%fZ','now') WHERE id=?`; commit; return 200 with the updated Task.

    Keep all float math server-side — the client only ever sends `{status, after_id}` intent (locked design: server owns ordering).
