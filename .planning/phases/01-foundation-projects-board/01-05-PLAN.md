<interfaces>
From plan 01-03 (use directly):
```ts
// types.ts
type Status = "todo" | "in_progress" | "in_review" | "done";
const STATUSES: Status[];                       // column order
const STATUS_LABELS: Record<Status, string>;    // "To Do" etc.
interface Task { id: number; project_id: number; title: string; description: string; status: Status; position: number; ... }
// queries.ts
useTasks(projectId: number): UseQueryResult<Task[]>   // key ["tasks", projectId], sorted by status, position
// mutations.ts
useCreateTask(projectId)                               // POST {title, description?} → lands at top of todo (server rule)
useMoveTask(projectId)                                 // optimistic; args { id, status, afterId: number | null }
```
Server move semantics (plan 01-02): `after_id: null` = top of target column; `after_id: <taskId>` = directly below that task; server computes position. Client NEVER sends position.

    Implement in `Board.tsx`:

    `handleDragOver({ active, over })` — LOCAL state only, no network:
    - Resolve `over` to a target column: if `over.id` is a string starting with `column:`, use that status; if it is a task id, use that task's current local column.
    - If the active task's local column differs from the target, splice it out of its column array and insert into the target (at the hovered card's index, or at the end for bare-column hover). This gives live cross-column preview.

    `handleDragEnd({ active, over })`:
    - Determine the final column and the active task's final index in the LOCAL `columns` state.
    - `afterId` = id of the card directly ABOVE the final index (`index === 0` → `null`); never the moving task itself.
    - Call `moveTask.mutate({ id: active.id, status: finalStatus, afterId })`; clear `activeTask` (unfreezing derivation). If `over` is null (dropped outside), just clear `activeTask` — derivation snaps local state back to query truth.
    - Same-position no-op (same column AND same index as drag origin) → skip the mutation entirely.

    Reconciliation rules (Pitfall 6 — verify they hold after wiring): columns derive ONLY from `useTasks` data when no drag is active; the optimistic cache write in `useMoveTask.onMutate` keeps the post-drop order stable until `onSettled` invalidation brings server truth; on error the snapshot rollback in the mutation restores the cache and the derived columns revert (no manual rollback code in Board.tsx). No spinners during drag (UI-SPEC).
