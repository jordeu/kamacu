<objective>
Persist per-file "Viewed" state server-side so it survives reopen + restart (DIFF-03) and auto-resets when a file's rendered diff changes (DIFF-04). Add the `00011_diff_viewed` migration, merge Viewed onto the existing GET diff response, and add the `PUT /api/tasks/{id}/diff/viewed` write endpoint.

Purpose: The Viewed state is keyed by the rendered-diff hash from Plan 01, using a keep-history table (row per `(task_id, file_path, diff_hash)`) so reverting to a previously-viewed diff restores the checkmark and a changed file's new hash simply has no row.
Output: New DB table (goose `00011`), read-merge + write endpoint in `internal/api/diffs.go` (inline store helpers, hand-written `database/sql`), and Go tests covering read/write/keep-history/FK-cascade.
</objective>

diff.File now has: Hash string `json:"hash"` (populated by Compute) and Viewed bool `json:"viewed"` (default false; this plan populates it in the handler).

PUT request body shape (client sends the hash it just rendered — do NOT re-Compute to validate it):
  { "path": string, "hash": string, "viewed": bool }
Response: 204 No Content (client's onSettled invalidate re-reads authoritative state).
</interfaces>

<notes>
- **Store location:** implement the three SQL statements as inline helpers in `internal/api/diffs.go` (hand-written `database/sql`) — PATTERNS confirms inline-in-handler or a new `internal/diffviewed` package both match house style; inline keeps this plan's footprint tight. `?` placeholders ONLY — never string-concatenate `path`/`hash`/`id` into SQL (T-18-01).
- **Trust the client hash on write; do NOT re-`Compute`** (RESEARCH §Area 2). A stale/garbage row never matches the current rendered hash on the next open (so it shows un-viewed — correct) and is cascade-pruned on task delete. Re-computing buys nothing and contradicts the locked design.
- **No startup backfill.** An empty `diff_viewed` on first boot is correct — do NOT add a `BackfillProjectIcons`-style hook.
- **Binary strict-D-01 limitation** carries through: a binary file's hash is header-constant (Plan 01 `<notes>`), so marking a binary Viewed persists against that constant hash and will not reset on a byte change. Accepted.
</notes>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → API (`PUT /api/tasks/{id}/diff/viewed`) | The one new write surface this phase. Untrusted request body (`path`, `hash`, `viewed`) crosses here. Localhost single-user — no auth/session boundary exists by design (CLAUDE.md). |
| API → SQLite (`diff_viewed`) | User-supplied `path`/`hash` strings are persisted; must never be interpolated into SQL. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-01 | Tampering | SQL injection via `path`/`hash` on the PUT write / GET read | mitigate | `?` placeholders only for all four statements (SELECT/INSERT/DELETE + id lookup); never string-concatenate (T-18-01, icons.go:183). Task 2 acceptance grep enforces this. |
| T-22-02 | Info disclosure | Cross-task Viewed leakage | mitigate | Every statement scoped `WHERE task_id = ?`; composite PK includes `task_id`; the FK insert fails for a non-existent task and `pathID`→404 rejects a bad id. |
| T-22-03 | Denial of service | Unbounded `path`/`hash` sizes on the viewed write | mitigate | Reject empty `path`, `path` > 4096 bytes, and any `hash` not exactly 64 lowercase hex chars (400). Bounds the row size and rejects garbage cheaply. |
| T-22-04 | Tampering | Client writes a `path`/`hash` not in the task's current computed diff | accept | Local-only single-user; no privilege boundary. A well-formed-but-not-current row is harmless keep-history scoped to a valid `task_id` (FK-enforced), never matches the current rendered hash on the next open (→ shows un-viewed, correct), and is cascade-pruned on task delete. Re-`Compute`ing to validate the path would contradict the locked "trust client hash, no re-Compute" design (RESEARCH §Area 2) for no real-world benefit on localhost. |
| T-22-SC | Tampering | npm/go package installs | accept | This plan adds NO packages (`crypto/sha256`, `database/sql`, goose, ServeMux all pre-imported). No install → no legitimacy gate needed (RESEARCH Package Legitimacy Audit: zero new registry packages). |

No high-severity threat remains open. V2/V3/V4 (auth/session/access-control) not applicable — localhost single-user by design.
</threat_model>
