### 🚧 v1.9 Workspaces (Phases 25–26) — IN PROGRESS

**Milestone Goal:** Group projects into named workspaces (e.g. "Personal", "Professional"), switchable from the top of the expanded projects sidebar, while the global Active Sessions bar keeps showing agent work across every workspace.

- [ ] **Phase 25: Workspace Data Foundation** - `workspaces` table + `projects.workspace_id` FK (migration 00012) with an idempotent startup backfill assigning every existing project to a protected default **Personal** workspace.
- [ ] **Phase 26: Workspace Switcher, Management & Assignment** - Sidebar workspace switcher (expanded-only) with add/rename/delete, per-workspace project filtering + navigation, project transfer via the `⋯` menu, create-in-active-workspace, and the cross-workspace sessions-bar guardrail.

## Phase Details

### Phase 25: Workspace Data Foundation
**Goal**: Every project belongs to exactly one workspace, with all existing projects migrated into a protected default **Personal** workspace — the data layer the switcher UI (Phase 26) builds on.
**Depends on**: Phase 24 (prior milestone; extends the existing schema at migration 00012)
**Requirements**: WSDATA-01, WSDATA-02
**Success Criteria** (what must be TRUE):
  1. A `workspaces` table and a `projects.workspace_id` foreign key exist (migration 00012), enforced NOT NULL so a project can never be workspace-less.
  2. On first startup after upgrade, a default **Personal** workspace is created and every pre-existing project is assigned to it — all projects remain intact and accessible.
  3. The startup backfill is idempotent: restarting never creates a second Personal workspace or reassigns projects (mirrors the existing `BackfillProjectIcons` startup hook).
  4. The projects API carries `workspace_id` on the wire, ready for the Phase 26 switcher to filter on.
**Plans**: TBD

### Phase 26: Workspace Switcher, Management & Assignment
**Goal**: Users can create, rename, and delete named workspaces, switch the active one from the sidebar, and assign projects to workspaces — while the global Active Sessions bar stays cross-workspace.
**Depends on**: Phase 25
**Requirements**: WSMGMT-01, WSMGMT-02, WSMGMT-03, WSMGMT-04, WSNAV-01, WSNAV-02, WSNAV-03, WSPROJ-01, WSPROJ-02, WSBAR-01
**Success Criteria** (what must be TRUE):
  1. A workspace switcher sits at the top of the projects sidebar in its **expanded state only** (hidden in the collapsed icon rail); opening it lists all workspaces, lets the user pick the active one, and reaches add / rename / delete.
  2. The sidebar project list — expanded rows AND the collapsed icon rail — shows only the active workspace's projects; switching navigates to that workspace's first project (or a clear empty state when it has none), and the active workspace survives a reload (persisted in `localStorage`).
  3. User can create a workspace by name and rename any workspace including Personal; deleting a workspace that still holds projects is blocked with a clear "transfer or remove its projects first" message, and the default Personal workspace can never be deleted (at least one workspace always exists).
  4. User can transfer a project to another workspace from its existing `⋯` menu, and a newly created project lands in the currently active workspace.
  5. The global Active Sessions bar keeps showing agent sessions across every workspace, unaffected by the active-workspace filter (non-regression of the existing cross-project bar).
**Plans**: TBD
