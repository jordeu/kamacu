# S01: Agent data foundation and spawn engine

**Goal:** Stand up the agents data layer (table, seed, projects.agent_id FK + backfill), the /api/agents CRUD with delete-guard and set-default, and the spawn-engine branch on agent.engine — proving the claude path is byte-for-byte unchanged (fake-claude tests green) and a custom-engine spawn renders the command template in the worktree PTY with running/exited status.
**Demo:** After this: a custom agent row can be created via API, a project assigned to it, and spawning that project's task runs the agent's command in the worktree PTY with running/exited status; a claude project still shows working/waiting + resume.

## Must-Haves

- migration 00013 creates the agents table (name, command, engine, is_default, is_system) + seeds the claude agent (is_system=1, is_default=1, engine='claude', command='claude') and adds projects.agent_id FK (NOT NULL DEFAULT <claude-id> REFERENCES agents(id) ON DELETE RESTRICT), backfilling every existing project to the default — all in one migration using the 00012 NO TRANSACTION + PRAGMA foreign_keys=OFF/ON shape.
- BackfillAgents startup hook (mirroring BackfillWorkspaces at workspaces.go:29) runs after store.Migrate in main.go (right after BackfillWorkspaces) and is idempotent: guarantees exactly one is_default=1 agent exists, no-op if the seed is already present.
- A staged-upgrade test (existing DB -> migrate 00013 -> every project under the default agent, tasks intact, exactly one default, idempotent re-run) passes, mirroring the 00012 workspaces staged test.
- /api/agents CRUD at internal/api/agents_crud.go (or agents.go): list (default-first then alpha), create (name+command+engine default 'custom'), update (is_system row: name+command only; engine immutable), delete (409 blocked when is_system=1 OR when COUNT(projects WHERE agent_id=?)>0), set-default (transactional exactly-one). Reuses the workspaces.go handler shape, scanAgent, agentColumns.
- projects.agent_id threaded through projectColumns/scanProject so GET/POST/PATCH /api/projects all carry it; POST defaults agent_id to the current global default agent (read-at-use, no restart).
- Spawn engine branches on the resolved agent.engine: 'claude' builds today's exact argv (session-id/resume/--settings overlay/quota) BYTE-FOR-BYTE; 'custom' renders the command template (shell-words split, cwd=worktree, {{worktree}}/{{session_id}} substitution).
- Custom-agent sessions report running/exited only; no hook overlay, no BEL scanning, no --resume; on process exit the session marks dead (same path as a bash tab).
- The existing fake-claude spawn tests pass UNCHANGED (regression proof the claude argv is byte-for-byte preserved).
- New unit tests: custom-engine command-template render (shell-words split + {{worktree}}/{{session_id}} substitution) covering quoted args, spaces in paths, missing/unknown placeholders; delete-guard (is_system + in-use); set-default exactly-one invariant.
- go test ./..., go vet ./..., make test all green.

## Proof Level

- This slice proves: automated-plus-staged-upgrade

## Integration Closure

Spawn resolves the project's agent_id -> agents.engine at task spawn time (read fresh inside the POST /api/sessions agent handler, alongside the existing worktree_path read). The claude path and custom path share only the PTY/session plumbing (Manager.Spawn + the Session struct), not the argv builder — the branch is inside Manager.Spawn's KindAgent block. projects.agent_id is threaded through projectColumns/scanProject on all of GET/POST/PATCH /api/projects, both create paths defaulting to the global default agent. The /api/agents CRUD is self-contained, mirroring the workspaces.go seams.

## Verification

- Custom-agent spawns log agent id+name+engine at spawn (slog, no secrets). A custom-agent spawn failure (binary not on PATH via LookPath, or template render error) returns a clear error to the API caller (mirrors the existing "claude binary not found on PATH" error at manager.go:163) and is logged warn-level. The engine branch chosen is observable in the spawn log line.
