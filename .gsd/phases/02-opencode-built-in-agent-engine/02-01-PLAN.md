# S01: opencode engine spawn and activity-based status

**Goal:** Add opencode as a third built-in agent engine ("opencode") that spawns in a task worktree PTY like claude and reports working/waiting/idle status by reusing the existing claude hook receiver unchanged. A seeded non-deletable opencode system agent row makes it selectable in the existing M001 UI; the spawn path injects KAMACU_SESSION_ID/KAMACU_HOOK_TOKEN/KAMACU_HOOK_BASE env so an env-gated on-disk opencode plugin (~/.config/opencode/plugin/kamacu-status.js) can curl /api/hooks/sessions/{id} with claude-compatible event names (permission.ask→Notification, session.idle→Stop, session.created→SessionStart). The claude and custom spawn paths are unchanged byte-for-byte.
**Demo:** After this: create a task with the opencode agent, watch it launch in the terminal, status toggles working/idle as it runs.

## Must-Haves

- Migration 00015 seeds a non-deletable (is_system=1) opencode agent row (engine='opencode', command='opencode', is_default=0); BackfillOpenCodeAgent guarantees it idempotently at startup; claude remains the sole is_default=1 row (R019 invariant intact).
- manager.Spawn injects KAMACU_SESSION_ID=<id>, KAMACU_HOOK_TOKEN=<token>, KAMACU_HOOK_BASE=<baseURL> into the opencode process env (gated to engine=="opencode"); the claude and custom env postures are byte-for-byte unchanged.
- agentStatusLocked() treats engine=='opencode' as a full-heuristics engine (working/waiting/idle), NOT the custom 'running' collapse; the claude and "" back-compat paths are unchanged.
- hooks.go is unchanged (engine-agnostic); the opencode plugin emits only SessionStart/Stop/Notification.
- internal/opencode leaf package embeds kamacu-status.js and idempotently installs it to ${XDG_CONFIG_HOME:-~/.config}/opencode/plugin/ ONLY when the opencode config dir already exists (no pollution for non-opencode users); the plugin no-ops unless KAMACU_SESSION_ID is set.
- Tests pass: opencode-engine session reports a heuristic status (working/idle/waiting), never 'running'; opencode spawn env carries the three KAMACU_* vars (verified via a stub that records env); plugin install is idempotent and content-correct (gating + event names); POSTing Notification/Stop/SessionStart to an opencode session drives waiting/idle/hooksAlive transitions.
- The fake-claude regression suite (internal/session/agent_test.go) and the custom-engine tests (agent_engine_test.go) pass UNCHANGED — no claude/custom regression (R016/R017).

The opencode seed appears in the existing agent dropdowns automatically (M001 R021/R022 UI needs no change for SELECTION); a dedicated 'opencode' engine badge label is cosmetic and may be polished in a later slice.

## Verification

- Runtime signals: an opencode-engine session's Info().AgentStatus now reflects hook-driven working/waiting/idle (previously collapsed to 'running' under the custom gate). The hooksAlive canary (flipped by the SessionStart hook POST) is the diagnostic for "the plugin successfully reached the hook receiver" — if it never flips, the plugin/env path is broken.
- Inspection surfaces: GET /api/sessions .status for an opencode task; `SELECT name,engine,command,is_system FROM agents WHERE engine='opencode'`; the managed plugin file at ~/.config/opencode/plugin/kamacu-status.js (carries a kamacu-managed header).
- Failure visibility: a missing/unreachable plugin or unset KAMACU_SESSION_ID leaves the opencode session stuck on 'working' (lastActivity from PTY output) with hooksAlive=false (BEL fallback stays armed) — a future agent localizes this by checking whether status ever reaches 'idle' and whether hooksAlive flipped after spawn.
- Redaction constraints: KAMACU_HOOK_TOKEN is injected via env and posted only to loopback; never logged (slog). Same trust boundary as claude's --settings overlay (which also exposes the token to the spawned process).
