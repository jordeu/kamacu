# Native Pi Agent implementation plan

Add Pi as a built-in Kamacu agent for projects, per-task overrides, and Scratchpad. Run Pi's interactive terminal through the existing PTY path, support Start, Stop, Reset, and Resume, and offer a per-task model picker. Extend the opt-in Kamacu integration to install Pi's project context instructions and register its MCP tools. Use the host's Pi installation and provider configuration. Pi 1.6.1 is the initial compatibility baseline to test. The Kamacu baseline is `origin/master` at `2a10673`, which includes file-based project context.

## Model selection

Yes. Pi accepts `--model provider/model-id`, so Kamacu can reuse its existing model catalog, model argument, and task override. Provider qualification matters because the same model ID can be available through several providers. A task choice applies on the next Start or Resume. **Agent default** leaves the model choice to Pi, including its saved conversation model on resume. Users can also switch models in Pi's terminal with `/model` during a run. The task setting remains the requested model for the next launch. Scratchpad uses the chosen Pi agent's defaults under its existing settings contract. [Pi command line](https://docs.pi.dev/latest/cli) · [Pi model selection](https://docs.pi.dev/latest/models)

Use Pi RPC for catalog discovery while keeping interactive mode for sessions. `get_available_models` provides structured provider and model IDs. Pi also offers `--list-models` for diagnostics and RPC `set_model` for clients that own the agent process. Kamacu's terminal provides the existing interaction and monitoring surfaces, so the first implementation needs neither a custom RPC UI nor a Node SDK dependency. [Pi RPC](https://docs.pi.dev/latest/rpc) · [Pi RPC commands](https://docs.pi.dev/latest/rpc-commands)

## 1. Register Pi and launch its terminal

- Add a migration for a non-default system agent with `engine=pi`, command `pi`, and model argument `--model {{model}}`. Follow the existing seed and startup backfill patterns in `internal/api/agents_backfill.go` and `cmd/kamacu/serve.go`. Handle existing custom agents named Pi without reassigning their projects or overwriting their settings.
- Add `pi` to the web agent type and verify selection in project settings, the task editor, and Scratchpad. Resolve the executable on the Kamacu server host and return a Pi-specific error when it is missing or lacks the required CLI capabilities.
- In `internal/api/sessions.go` and `internal/session/manager.go`, reuse the native non-Claude argv and PTY path. Launch in the task worktree or Scratchpad root with the host's Pi configuration, auth, and normal project trust behavior. Reserve Kamacu-managed session flags and reject conflicting flags such as `--no-session` and `--continue` in the native Pi command. Keep command arguments as separate argv entries. Document host installation, provider login, and Pi's project trust behavior. [Pi project trust](https://docs.pi.dev/latest/security)

## 2. Connect Pi discovery to the existing picker

- Extend `internal/api/models.go` and reuse `AgentModelsEditor`, the new task dialog, and `TaskAgentSettings`. Start a bounded `pi --mode rpc --no-session` discovery subprocess, send one correlated `get_available_models` request, and decode only the matching successful response. Disable MCP and automatic extension loading in the default discovery probe. Reuse the endpoint's timeout, output bounds, and process-group cleanup. Close the probe promptly on response or cancellation. Return distinct errors for unsupported Pi, startup failure, and malformed output, and treat an empty catalog as a valid result.
- Return deduplicated `provider/id` values, preserving any slashes inside the model ID. Discovery supplies suggestions. Saving an agent's model list controls what users can pick. Keep manual entries and the existing discovery-command override for trusted extension-provided catalogs or launch-specific configuration. Use the existing requirement for an explicit discovery command when the agent command contains launch arguments.
- Apply the saved task override on fresh and resumed launches. Test precedence when the configured command also supplies a model or provider selector, and reject conflicting options when Kamacu cannot apply the task choice unambiguously. Pi can accept an unknown ID at startup. For configurations the discovery probe can represent, validate explicit choices against an exact provider and model ID match before launching and report a stale selection with a way to pick another model. For extension or custom discovery catalogs, use the explicitly configured discovery command where available and surface Pi's runtime errors through the terminal and monitor. Keep provider credentials and provider configuration in Pi.

## 3. Persist the conversation and resume it exactly

- Add nullable `pi_session_id` columns to `tasks` and `global_task`. Give every fresh launch a new ID with `--session-id <uuid>` and an explicit `--session-dir` under Kamacu's private data directory, scoped to the task or Scratchpad. Store the ID only after a successful PTY spawn, with writes ordered under the task or Scratchpad lifecycle lock. A failed reset should preserve the previous resume reference.
- Derive resumability from the ID and an actual saved Pi JSONL transcript. Resolve the file within the managed directory and verify its header ID and working directory before offering Resume and again before launching `--session <uuid>` with the managed session directory. Pi’s ID lookup rejects a missing transcript before opening it. Pi can defer writing the file and can open a missing path as a new conversation. Return a conflict if the transcript is missing, ambiguous, or belongs to a different working directory. Retain older transcripts when Reset selects a new ID.
- Use one Pi resume check across the task and Scratchpad summaries in `internal/api/agents.go`, session creation, Pending Status Check in `internal/api/pending.go`, and the inbox's start-or-resume decision in `internal/notifications/execution.go`. Update `internal/api/global.go` so a Scratchpad root or agent change clears its Pi reference. Cover server restart and enforce the one-running-conversation guard across entry points.
- Keep the resume reference tied to the conversation Kamacu launched. Document that Pi's `/new` and `/resume` can switch the conversation inside the terminal and that Kamacu's Reset and Resume manage its tracked conversation. For recurring tasks, start each successor with its own Pi conversation and worktree. Existing engines copy conversation IDs on recurrence, and Pi opens a session in its recorded directory. Following Pi's in-terminal session switches or explicitly forking a conversation into a new worktree can be added as separate lifecycle features. [Pi sessions](https://docs.pi.dev/latest/sessions) · [Pi session file format](https://docs.pi.dev/latest/session-format)

## 4. Install project context instructions and MCP tools

- Add `pi` to `internal/integration`, the `kamacu integration` CLI, and the Settings → Agents integration panel. Resolve Pi's agent directory consistently for context instructions and MCP using `PI_CODING_AGENT_DIR` or `~/.pi/agent`. Use the existing Enable, Repair, Remove, and startup sync flow for both resources. Document the managed paths and report context installation or repair errors alongside MCP status. [Kamacu agent integration](agent-integration.md) · [Pi configuration](https://docs.pi.dev/latest/configuration)
- Extend `internal/integration/instructions.go` to install the existing marked block in the effective global Pi context file. Pi 1.6.1 checks `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, and `CLAUDE.MD` in that order and loads the first readable regular file. An empty override still wins. Create `AGENTS.md` when no candidate exists. Preserve the active fallback and surrounding guidance. Reuse the existing ownership, atomic writes, and repair and removal logic. If a higher-priority path appears later, refresh the effective path on repair and report files Kamacu cannot safely edit, including active instruction-file symlinks. Pi's worktree and ancestor context files continue to load through its own discovery. Document that `--no-context-files` disables discovery of the installed block. [Pi configuration](https://docs.pi.dev/latest/configuration) · [Pi command line](https://docs.pi.dev/latest/cli)
- Reuse `AgentConfig.ProjectContext` in `cmd/kamacu/serve.go` and `internal/session/manager.go`. For an opted-in Pi task, resolve the project's directory through `projectcontext.PrepareForLaunch` on Start and Resume, refresh shared skill links, and inject the absolute `KAMACU_PROJECT_CONTEXT`. The global block directs Pi to read the project's current `instructions.md` and matching skills, following directory symlinks to supporting files. The files already live in Kamacu's per-project context folders and shared skill library. The installer writes the instruction block to the Pi profile and leaves project files in their existing locations. Reuse stale environment stripping and the existing project deletion handling. Scratchpad, shells, custom agents, and opted-out Pi launches receive no project context.
- Register `kamacu mcp serve` in the user-level `mcp.json` using Pi's built-in stdio MCP. Preserve existing entries and wire the current task/session IDs and bridge connection settings through runtime environment references. Verify context access with Pi's ordinary file tools and verify MCP with a real artifact tool call. Report project settings or extensions that override Pi's built-in MCP registration. [Pi MCP servers](https://docs.pi.dev/latest/mcp)

## Verification and rollout

- **Verified with local Pi 1.6.1.** A disposable configuration exposed the same `shared/name` ID under two fixture providers, returned both through RPC discovery, and selected the requested provider with the qualified CLI flag. Reopening a fixture transcript with a different model preserved its session ID and selected the new provider. A fresh launch reported a session path before writing a file. A missing explicit path created a new in-memory conversation, and an unknown model ID was accepted into state. Pi's MCP CLI wrote the expected registration with a literal environment reference.
- **Launch and resume acceptance.** Cover seed upgrades and name collisions, the missing binary, exact argv and working directory, empty and stale resume targets, concurrent starts, failed and successful resets, Scratchpad root changes, recurring worktrees, Pending Status Check, and inbox-driven resume. Confirm other engine launch and resume tests still pass.
- **Model acceptance.** Cover empty, malformed, oversized, and timed-out discovery, duplicate IDs across providers, nested model IDs, custom discovery commands, and explicit versus default model selection. Use a local mock provider to exercise a full turn, real transcript creation, restart and resume, stale model errors, and the task picker. The discovery checks above sent zero inference requests.
- **Context and tools acceptance.** Pi 1.6.1's installed resource loader was verified against a disposable profile with all five global filenames, including an empty override and a separate worktree `AGENTS.md`. Extend the integration and project context tests to cover a custom Pi directory, conflicting or edited blocks, precedence changes on repair, and non-regular files. Verify Start and Resume receive the correct project directory, see edits and refreshed skill links, and exclude Scratchpad and opted-out launches. Use a real Pi session to verify the installed block leads to reading `instructions.md` and a linked skill's supporting file, then verify MCP artifact calls with both task and Scratchpad identity. Exercise removal and preservation of user edits for both files.
- **Monitoring acceptance.** Replay Pi terminal recordings through Kamacu's monitor and exercise a browser session from task creation through model selection, Start, Stop, and Resume.

Land the built-in agent, launch and resume, and model picker together. Include the context installer and MCP adapter before exposing Pi's Enable integration action.
